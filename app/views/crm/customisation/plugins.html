When to use a plugin

Use a plugin when the logic:

  • must run before or during a save, such as validation before data is committed
  • must always run, including for bulk imports and API calls, or fail with an error
  • needs to be part of a transaction that rolls back if something fails
  • is too complex, too slow or too unreliable to build in Power Automate
  • applies rules across several tables where order and timing matter

Avoid plugins that override the platform's default behaviour.

Microsoft explains how plugins work (opens in a new tab), and publishes best practice for business logic (opens in a new tab). Follow both.

DfE standards

  • Give each plugin class one responsibility, and don't combine unrelated logic.
  • Register steps only on the messages and tables you need, and use filtering attributes so plugins only run when relevant columns change.
  • Use the pre-operation stage to validate or change the record being saved, and the post-operation stage to create related records. Call other services from asynchronous steps, so the user isn't kept waiting and a slow service can't time out the save.
  • Keep calls to Dataverse inside a plugin to a minimum.
  • Write clear, actionable error messages that don't expose sensitive information.
  • Keep plugin code in source control with the solution, and update the assembly version with each change.
  • Deploy plugins only in managed solutions, through the Azure DevOps pipelines.
