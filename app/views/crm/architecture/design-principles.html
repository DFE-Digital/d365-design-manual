All DfE Dynamics 365 solutions must follow these principles. Any exception must be agreed with the SDT CRM Design Authority and documented. The CRM strategy explains why they matter.

Use the platform before building

  • Use out-of-the-box Dynamics 365 features first, then low-code, and pro-code only as a last resort. See configuration, low-code and pro-code.
  • Choose the simplest design that meets the need, and challenge requirements that add complexity without clear value.
  • Use the wider Power Platform rather than custom code: Power Automate for automation and lightweight integration, Power Apps where the Dynamics 365 apps don't fit, and Power BI for analytics.
  • Use Power Pages for external-facing services, built on the DfE Power Pages framework and its reusable features, so business users can manage content without a developer.

Design for people, not the data model

  • Design forms, views and navigation around what each user role needs to do.
  • Remove fields and steps that users don't need.
  • Check designs with user feedback and testing.

Build for reuse

  • Build generic functionality that other services can use, rather than functionality tied to one team.
  • Use the shared patterns and components before building your own.
  • Split functionality into solutions that follow the standard solution model, so a service can be deployed and changed on its own.

Put logic in the right place

  • Keep form scripts and business rules to user experience and simple validation.
  • Put business logic and validation that must always apply on the server, so it also runs for imports, flows and the API.
  • Keep integrations separate from business logic.
  • Give external systems a stable interface, such as a custom API, rather than exposing the Dataverse data model.

Keep components small and independent

  • Give each plugin, flow or script one clear purpose.
  • Avoid dependencies between components, so a change in one doesn't break another.
  • Prefer asynchronous and event-driven integration, so one system doesn't wait on another.

Design for volume and failure

  • Run long or heavy processing asynchronously.
  • Limit synchronous logic on events that happen often, and the data loaded on forms, views and dashboards.
  • Plan for growth in users and data from the start.
  • Design integrations to retry, log failures where support teams can see them, and catch up when a service comes back.
  • Avoid single points of failure, and don't add custom dependencies that reduce the platform's availability.

Build security in

  • Give users and application users only the permissions they need.
  • Control access with the standard security model: business units, security roles and teams.
  • Secure integrations and automation as carefully as user access.

Stay supportable

  • Only use methods Microsoft supports.
  • Design for Microsoft's regular updates, and for future change.
  • Record key design decisions.
