Microsoft explains how to create and edit views (opens in a new tab), and the difference between public and personal views. Follow these standards when you do.

Public and personal views

  • Use public views, managed in your solution, for main lists, dashboards, subgrids and anything many users rely on.
  • Personal views are fine for a user's own ad hoc filtering. If a shared personal view becomes something a team relies on, replace it with a public view.
  • If a team needs a shared view that isn't in a solution, create it with a service account rather than a person's account, so it isn't lost when that person leaves.
  • To show a public view to some teams only, restrict it by security role. This only hides the view: users still only see records their roles allow.

Columns, sorting and filters

  • Use 6 to 10 columns, and only the ones users need to scan the list or make a decision.
  • Use the same columns in the same order across similar views. For example, every case view shows Case title, Case type, Contact, Organisation, Status Reason, Owner and Created On.
  • Sort by the column that matters most for the task, such as Created On, newest first, for triage.
  • Filter out noise by default, such as showing open cases rather than all cases.
  • Use the same default sort across views of the same table.

Quick Find

  • Only include columns users actually search on, such as case reference, contact name, organisation name and email address.
  • Keep it to fewer than 10 columns, to keep search fast and relevant.

Names

Use names like:

  • All Active Cases
  • My Active Cases
  • All Resolved Cases
  • My Resolved Cases

Don't use internal abbreviations, programme shorthand or technical names.

Design views with the people who will use them, around tasks such as triage, complaints, application review or quality assurance.
