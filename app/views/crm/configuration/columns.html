Microsoft's guidance explains the column types available in Dataverse (opens in a new tab), including formula columns (opens in a new tab). Follow these standards when you add columns.

Naming

  • Use clear, plain English names, such as Provider type rather than PType.
  • Use singular names, such as Application status.
  • Don't include the table name or programme abbreviations.
  • Use the same patterns across tables, such as Start date and End date.
  • Use the right publisher prefix.

Descriptions

Every column you add must have a description that explains what it holds, how it's used and any rules that apply to it. Data teams use these descriptions to build data dictionaries.

Yes or no questions

If a user answers the question through a portal, use the DfE yes/no choice (dfe_dfeyesnooptionset) from the DfE Core solution, not a native Yes/No column. Don't set a default, so the answer stays blank until the user chooses. A native Yes/No column always holds yes or no, so it can't tell an unanswered question apart from "No".

Use a native Yes/No column for flags that only the CRM sets, such as "Show on portal".

Choice or lookup

Use a choice column when:

  • the list is small and fixed
  • the options don't need any extra data

If more than one table uses the same options, use a global choice so they share one list.

Use a lookup to a table when:

  • the values change over time and users need to manage them as reference data
  • the value is a real thing, such as an organisation, team, region or programme
  • the value has its own details, such as a provider's UKPRN or address

Choice columns hold a number and a label, so think about how they'll appear in Power BI and exports.

Relationships

  • Use one-to-many relationships by default.
  • Only use many-to-many relationships when there's no data about the link itself. They are harder to show on forms and to search.
  • Choose the relationship behaviour deliberately, and test cascade behaviour before release, because it can delete or reassign records you didn't intend.

Microsoft explains the relationship behaviours (opens in a new tab).

Before you add a column

  • Check whether an existing column already holds the same information.
  • Make it generic, so other services can use it.
  • Use standard patterns, such as Status and Status Reason, instead of building your own.
  • Check whether it holds sensitive data that needs column security.
