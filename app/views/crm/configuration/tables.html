Use Microsoft's tables first

Use the standard Dataverse tables before creating your own, and don't create custom tables that duplicate them:

  • Account for organisations, such as schools and providers
  • Contact for people
  • Case for enquiries and case management

Standard tables work with Dynamics 365 features and get Microsoft's new features as they're released.

Design tables for reuse

DfE CRMs are shared by several services, so design tables that other services could use. For example, create an Application table, not an Apprenticeship Provider Application table.

Before creating a table:

  • check whether an existing table already holds the same thing, including in the shared components
  • consider adding columns to an existing table instead
  • follow DfE data standards where they exist, especially for organisations, contacts, providers and locations

Naming and publisher prefixes

  • Use a singular display name, such as Provider or Funding Application, and a natural plural for the plural name.
  • Make the purpose clear from the name, and don't use programme abbreviations or internal jargon.
  • Choose the name carefully. You can change a display name later, but not the schema name, so the two can drift apart.

The publisher prefix shows who a component belongs to:

Which publisher prefix to use
Component Prefix Example
A DfE-wide standard, for use in any CRM, or a core DfE service dfe_ The DfE yes/no choice in the DfE Core solution
Core to one CRM, and shared by the services in it The CRM's prefix rds_ or dcass_
Specific to one service within a CRM The service's prefix fst_ for a fostering table in the RDS CRM

Each prefix has its own publisher, and goes in the matching solution in the standard solution model.

Descriptions

Every table must have a description that explains what it holds and why. Data teams generate data dictionaries from solution metadata, so the description is how they understand the table.

Table type and ownership

You can't change a table's type or ownership after you create it.

  • Use user or team ownership when access depends on the team or person.
  • Use organisation ownership for reference data and configuration tables.
  • Only use an activity table for communications or events that appear on the timeline with other activities.
  • Avoid virtual tables unless an integration needs one, because they have limitations.

Microsoft's guidance on tables in Dataverse (opens in a new tab) explains the options.
