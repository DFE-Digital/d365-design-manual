Server logic looks like ordinary JavaScript, but it isn't a browser and it isn't Node.js. Microsoft's documentation misses a lot of the behaviour on this page. We found it while building DfE services, and we'll keep adding to it.

If a script is failing now, start with how to debug the generic error and the checklist.

The generic error

Most problems on this page show up the same way. The browser gets back:

{
  "requestId": "83f812f5-f85b-43be-8064-9121c2ce2438",
  "success": false,
  "serverLogicName": "MyServerLogic",
  "error": "Exception occurred while processing this request"
}

This means the platform stopped the script. Your own try and catch didn't run, so adding more error handling won't help, and nothing useful is logged. It can mean:

  • the script used JavaScript that crashes server logic
  • the script went over its memory limit
  • the request body was too big
  • the server logic record is broken

A script that returns your own error, with success: true and a message in data, did run: the problem is in your logic or a service it called.

JavaScript that crashes a script

Array methods that take a function

Don't use an array method that takes a function, such as .map(), .forEach(), .filter(), .some(), .reduce() or .sort() with a comparator. They crash the script with the generic error, even with no Dataverse calls involved. Use a for loop instead.

// Crashes
var doubled = [1, 2, 3].map(function (x) { return x * 2; });

// Works
var doubled = [];
for (var i = 0; i < numbers.length; i++) {
  doubled.push(numbers[i] * 2);
}

Functions created inside a loop

Don't create a function inside a loop. Declare it once, above the loop, and pass it what it needs.

// Crashes: a new function is created on every pass
for (var i = 0; i < rows.length; i++) {
  var row = rows[i];
  var getValue = function (fieldName) { return (row[fieldName] || "").trim(); };
  var value = getValue("some_field");
}

// Works: the function is created once
function getValue(row, fieldName) { return (row[fieldName] || "").trim(); }

for (var i = 0; i < rows.length; i++) {
  var value = getValue(rows[i], "some_field");
}

Nesting functions inside post() or get() is fine. The problem is only a new function on every pass through a loop.

When a script starts failing as it gets bigger, it's tempting to think it's hit a limit on the number of Dataverse calls. We thought that once, and were wrong: the real cause was one of these two patterns. Rule them out first. A script that really is too big for its memory limit is covered in the memory limit.

Blocked keywords and patterns

Power Pages checks scripts when you save them and rejects some keywords and patterns, even in code that would never run. If a script won't save, check it for these:

Dataverse calls

Results are wrapped twice

RetrieveMultipleRecords returns a JSON string. Inside it is an object with a Body property, which is another JSON string containing the records. Parse it twice.

var raw = Server.Connector.Dataverse.RetrieveMultipleRecords("accounts", "$select=name");
var wrapper = JSON.parse(raw);         // StatusCode, Body and so on
var records = JSON.parse(wrapper.Body).value;

Parse it only once and you'll get an error such as "Cannot read properties of undefined (reading 'length')". Write a small helper so you only get this right once:

function retrieveValue(entitySetName, odataOptions) {
  var raw = Server.Connector.Dataverse.RetrieveMultipleRecords(entitySetName, odataOptions);
  return JSON.parse(JSON.parse(raw).Body).value;
}

RetrieveRecord, CreateRecord, UpdateRecord and DeleteRecord return the same kind of wrapper. Check StatusCode or IsSuccessStatusCode before you use Body.

Calls run one at a time

Server.Connector.Dataverse calls aren't asynchronous, even though they might look as if they should be. Each one finishes before the next line runs, so await and Promise.all() make no difference to them.

// These run one after the other, whichever way you write them
var account = Server.Connector.Dataverse.RetrieveRecord("accounts", accountId);
var contact = Server.Connector.Dataverse.RetrieveRecord("contacts", contactId);

Server.Connector.HttpClient calls are asynchronous, and do need await.

Size and memory limits

Large requests hit several separate limits. Each one fails in a different way, which makes them easy to confuse.

Limits on large requests
Limit What you see What to do
JSON from the browser, about 1 MB A 500 error page from the platform, with RTGE01 and a blank message. The script never runs. Send the body as text/plain.
Script memory, 10 MB by default The generic error, often within a second. Small requests work, large ones fail, and the same request can work once and fail the next time. Raise ServerLogic/MaxMemoryUsageInBytes, and hold less in memory.
Department's application gateway, 2,000 KB A 403 Forbidden HTML page from Microsoft-Azure-Application-Gateway/v2, returned to your script as the service's response. Send less in each request. This limit can't be raised.
Run time, 120 seconds by default The generic error after about 2 minutes. Raise ServerLogic/TimeoutInSeconds (up to 240), or move the work to a background process.

Sending JSON from the browser

Power Pages reads application/json request bodies itself before passing them to your script, and rejects them over about 1 MB. A file sent as base64 reaches that at about 750 KB.

Send the same body with contentType: "text/plain; charset=utf-8" instead. Power Pages passes text straight through, and your script reads it in the same way, with JSON.parse(Server.Context.Body). Microsoft doesn't document this, so it relies on how Power Pages behaves now.

The memory limit

Each script runs with a memory limit, set by the site setting ServerLogic/MaxMemoryUsageInBytes. Microsoft removed the setting from its documentation in November 2025, but it still works. The default is 10 MB, and only about a third of that is available for your data.

Power Pages checks memory every 100 to 200 milliseconds rather than all the time. A script that goes over the limit but finishes quickly can get away with it. One that goes over and keeps running is stopped with the generic error. So failures can look random: the same request works once and fails the next time.

What uses memory:

  • Parsed data uses far more memory than text. Thousands of parsed objects can take several times the size of the JSON they came from.
  • Copies add up. The request body, the parsed object, a rebuilt object and the text you send on are all held at once.
  • Logging a whole payload keeps it in memory for longer, which makes a check more likely to catch it.

To handle large requests:

  1. Set ServerLogic/MaxMemoryUsageInBytes to 41943040 (40 MB). Type the name exactly: Power Pages ignores other spellings without telling you.
  2. Don't parse a large body if you're only passing it on. Check what you need with a string search, or send the values you need to check in the query string, and forward Server.Context.Body as it is.
  3. If you must build a large body, build it as a string rather than as objects.
  4. Don't log request bodies, files or results.
// Forwards a large body without parsing it
var raw = Server.Context.Body || "";
if (raw.indexOf('"files"') === -1) {
  throw new Error("Missing files array");
}

var response = await Server.Connector.HttpClient.PostAsync(SERVICE_URL, raw, headers, "application/json");

With 40 MB, we've virus scanned a 3.5 MB file (4.7 MB as base64) and validated a 3,000-row CSV file. A script that rebuilt 3,000 rows as objects before sending them on still went over the limit, and worked once it forwarded the text instead.

The memory limit's behaviour was first measured in 32 MB passes, 4 MB fails: what the Power Pages server logic memory limit actually does (opens in a new tab). Because the setting is undocumented, ask Microsoft to confirm it's supported before a service depends on it.

Calling services behind API Management

DfE APIs published through Azure API Management sit behind the department's application gateway. Its web application firewall rejects request bodies over 2,000 KB with a 403 Forbidden HTML page, before the request reaches API Management. The limit protects every service behind the gateway and can't be raised.

Design for it from the start if your data will grow. For example, send a reference to a stored file instead of the data itself, or send the data in batches.

Calling other services

  • Use a plain media type. The last argument of PostAsync, PutAsync and PatchAsync must be a media type on its own, such as "application/json". With a parameter, such as "text/plain; charset=utf-8", the call doesn't throw: it returns StatusCode 0 and "The format of value ... is invalid".
  • Stick to documented media types. Microsoft documents application/json, text/html and application/x-www-form-urlencoded. "text/plain" also works, but isn't documented. Large bodies sent as application/json from server logic aren't affected by the browser's JSON limit.
  • Check the status before you parse. Check IsSuccessStatusCode before you parse Body. An error page, such as the gateway's 403, isn't JSON.

Records, names and permissions

The URL uses the Name, not the Display name

Call /_api/serverlogics/<name> using the record's Name exactly as saved, including capital letters. A record with the Display name "Get account" and the Name GetAccount is only found at /_api/serverlogics/GetAccount. Check the record itself: names written in tickets, comments or documentation can drift from what's deployed.

You need two kinds of permission

Assign a web role to the server logic record, and give that web role table permissions on every table the script uses. They're set in different places and both are needed. Table permissions are shared, so once a role has them, every script using that role can use them too.

A record can break

Occasionally a record fails whatever code it has. If even this fails with the generic error, the record is broken, not your code:

function post() {
  return JSON.stringify({ test: "hello" });
}

Delete the record and create it again with the same Name, web roles and code.

Responses in the browser

  • Parse the response twice. Your return value is in the lowercase data property, as a JSON string, and sometimes the whole envelope arrives as a string too. Microsoft's documentation shows Data and Success with capital letters, but the API returns them in lowercase.
  • A 401 about the anti-forgery token. "The provided anti-forgery token was meant for a different claims-based user than the current user" means the page was loaded before the user signed in again, or has been open a long time. Reloading the page fixes it.
var envelope = typeof res === "string" ? JSON.parse(res) : res;
var result = JSON.parse(envelope.data);

How to debug the generic error

The generic error gives you nothing to go on, so find the cause by cutting the script down and building it up again.

  1. Check whether size is the problem. Try the same request with a small file or a few rows. If small requests work and large ones fail, read size and memory limits.
  2. Cut the script down to almost nothing. Read the request and return a small object, with no Dataverse or HttpClient calls. If that still fails, the record is probably broken.
  3. Add the rest back one piece at a time. Watch for array methods that take a function and functions created inside loops, which are easy to miss.
  4. Test one thing at a time. For example, to find out whether reading a large body or sending it on is the problem, test a version that only returns the body's length, then one that sends a large string it builds itself.

This is slow, but it's quicker than guessing.

Checklist

If a script fails with the generic error, check:

  • Does it use .map(), .forEach(), .filter(), .some(), .reduce() or .sort() with a comparator? Use a for loop.
  • Is a function created inside a loop? Move it above the loop.
  • Does it only fail with large requests? Check ServerLogic/MaxMemoryUsageInBytes is set and spelt exactly, and that the script doesn't parse, copy or log large data.
  • Is the browser sending large bodies as application/json? Send them as text/plain.
  • Does a version with no Dataverse or HttpClient calls still fail? Recreate the record.
  • Does the record have a web role, and does that role have table permissions on every table the script uses?
  • Are you parsing Dataverse results, and the response in the browser, twice?
  • Does the URL use the record's Name, exactly as saved?
