This page explains how to set up server logic on a site built from the base portal. Read behaviour and limitations as well: several things that work in a browser crash a server logic script.

Turn on server logic

Server logic is controlled by site settings. Add or check these on your website record.

Server logic site settings
Name What it does Value to use
ServerLogic/Enabled Turns server logic on or off for the site. true
ServerLogic/TimeoutInSeconds How long a script can run before it's stopped. The default is 120 seconds and the maximum is 240. Leave at the default unless a script needs longer. Keep requests from the browser short, and move long work to a background process.
ServerLogic/MaxMemoryUsageInBytes How much memory each script can use. The default is 10 MB, and only about a third of that is available for your data. Microsoft no longer documents this setting, but it still works. 41943040 (40 MB) on any site that handles uploaded files or large requests, such as the virus scan.
ServerLogic/AllowedDomains Limits which external domains server logic can call. By default, all domains are allowed. Optional. If you set it, include every service your scripts call.
! Warning Type the memory setting's name exactly: ServerLogic/MaxMemoryUsageInBytes. Power Pages ignores any other spelling, such as MaximumMemoryUsageInBytes, without telling you.

Your tenant's administrators can also block all calls from server logic to external services. If calls from your scripts to another service fail on every request, check with them.

Create a server logic record

  1. In Power Pages design studio, open your site and go to the Set up workspace.
  2. Select Server logic, then New server logic.
  3. Enter a name. The name becomes part of the URL: /_api/serverlogics/<name>. Use a short name in PascalCase, such as VirusScan, and don't change it once pages use it.
  4. Add a description that says what the script does.
  5. Assign the web roles of the users who'll call it.
  6. Give the same web roles table permissions on every table the script reads or writes.

A server logic record has both a Name and a Display name. The URL uses the Name, exactly as it's saved, including capital letters. Check the record itself rather than trusting a name written in a ticket or comment.

Both the web role on the record and the table permissions are needed. If either is missing, the script fails.

Write the script

A script defines a function for each HTTP method it accepts: get(), post(), put(), patch() or del(). Whatever the function returns is sent back to the browser. Return a JSON string, and include your own status in it, because you can't set the HTTP status code.

async function post() {
  try {
    const body = JSON.parse(Server.Context.Body || "{}");
    const recordId = Server.Context.QueryParameters["id"];

    // Your logic here

    return JSON.stringify({ status: "success" });
  } catch (err) {
    Server.Logger.Error("MyServerLogic failed: " + err.message);
    return JSON.stringify({ status: "error", message: "Something went wrong" });
  }
}

The script runs on the server, not in a browser or Node.js, so there's no fetch, window or document. Use the Server object instead.

What the Server object gives you
Property Use it to
Server.Context.Body Read the request body, as a string. Parse it yourself with JSON.parse.
Server.Context.QueryParameters Read query string values, for example Server.Context.QueryParameters["id"].
Server.User Get the signed-in user, for example Server.User.contactid. It's null for anonymous users. Take the user from here, never from the request.
Server.Connector.Dataverse Create, retrieve, update and delete records, and call custom APIs. Table permissions apply.
Server.Connector.HttpClient Call another service with GetAsync, PostAsync, PutAsync, PatchAsync or DeleteAsync. These are asynchronous, so use await.
Server.EnvironmentVariable.get(name) Read an environment variable, such as a service URL or key.
Server.SiteSetting.Get(name) Read a site setting.
Server.Logger Write to the server logic logs with Log, Warn or Error. Never log a whole request or file: it uses memory and makes failures more likely.

Microsoft lists everything available in server objects (opens in a new tab).

Keep keys and secrets out of the script

Don't type URLs, keys or other secrets into a script. Scripts are exported with the rest of the site, so anything in them ends up in solution files, portal downloads and source control.

Store them in environment variables instead, and read them with Server.EnvironmentVariable.get. For keys and other secrets, use a secret environment variable backed by Azure Key Vault. Each environment then has its own values, so you don't need to change the script when you deploy it.

const SERVICE_URL = Server.EnvironmentVariable.get("dfe_virusscanurl");
const SERVICE_KEY = Server.EnvironmentVariable.get("dfe_virusscankey");

Replace dfe_ with your solution's publisher prefix.

Call server logic from a page

Every request to server logic must include the site's anti-forgery (CSRF) token. The CRM helper framework adds it for you through webapi.safeAjax.

webapi.safeAjax({
  type: "POST",
  url: "/_api/serverlogics/MyServerLogic?id=" + encodeURIComponent(recordId),
  contentType: "text/plain; charset=utf-8",
  data: JSON.stringify(payload),
  success: function (res) {
    // The envelope, and its data property, can both arrive as strings
    const envelope = typeof res === "string" ? JSON.parse(res) : res;
    const result = JSON.parse(envelope.data);

    if (result.status !== "success") {
      // Show an error
    }
  },
  error: function () {
    // Show an error
  }
});

Send the body as text

Send request bodies with contentType: "text/plain; charset=utf-8", even though they contain JSON. Power Pages rejects JSON bodies over about 1 MB when they're sent as application/json, before your script runs. Sent as text, the same body gets through, and your script reads it in the same way, with JSON.parse(Server.Context.Body).

This relies on how Power Pages currently behaves, which Microsoft doesn't document. Small requests work either way, but using text for every request means you won't hit the limit as your data grows.

The response

Power Pages wraps whatever your script returns in an envelope. Your return value is in the lowercase data property, as a string.

// The script ran
{
  "requestId": "b0389493-25b2-4975-8352-1f23b242dfa5",
  "success": true,
  "data": "{\"status\":\"success\"}",
  "serverLogicName": "MyServerLogic"
}

// The script was stopped by the platform
{
  "requestId": "83f812f5-f85b-43be-8064-9121c2ce2438",
  "success": false,
  "serverLogicName": "MyServerLogic",
  "error": "Exception occurred while processing this request"
}

If success is false with that generic error, your own try and catch didn't run. See how to debug the generic error.

Call another service from server logic

HttpClient returns an object describing the response. Check IsSuccessStatusCode before you parse Body, because an error response might not be JSON.

const response = await Server.Connector.HttpClient.PostAsync(
  SERVICE_URL,
  JSON.stringify(requestBody),
  { "x-functions-key": SERVICE_KEY },
  "application/json"
);

const parsed = typeof response === "string" ? JSON.parse(response) : response;

if (!parsed.IsSuccessStatusCode) {
  throw new Error("Service returned " + parsed.StatusCode + ": " + (parsed.ServerErrorMessage || parsed.Body));
}

const result = JSON.parse(parsed.Body);
  • Use a plain media type for the last argument, such as "application/json". HttpClient rejects a media type with parameters, such as "text/plain; charset=utf-8", with a StatusCode of 0 and "The format of value ... is invalid".
  • If the service sits behind Azure API Management or the department's application gateway, requests are limited to 2,000 KB. See size and memory limits.

Deploy server logic to other environments

Server logic records and site settings are site components, so they move with your site's solution. Before you deploy:

  • check the server logic records, their web roles and table permissions are in the solution
  • check the ServerLogic/ site settings are in the solution, including ServerLogic/MaxMemoryUsageInBytes if you use it, because a setting that's only on the site can be lost
  • set each environment's values for any environment variables the scripts use

If you would like any additional advice or guidance with server logic, please contact the Solutions Delivery Team.
